## 二、建議

### S1 星系內部的「同專案」標籤全是自己的專案名稱(建議,高優先)

- 位置:`GalaxyView.tsx:173-178`(星系內部保留所有成員數 ≥ 2 的 `project` 連線)、`link-styles.ts` 的 `toLinkSegments`(每一對成員都畫一條線,標籤是專案名稱)。
- 情境:在「星核」星系裡,6 個成員兩兩之間都有「同專案:星核」連線,最多 15 條線、15 個「星核」標籤,截圖上整片都是「星核」。在星系內部,所有成員本來就同專案,這些線和標籤沒有任何資訊,還會蓋住交辦、會議等真正有意義的連線。
- 修法建議:
  - 星系內部**移除專案名稱等於這個星系名稱的 `project` 連線**(線和標籤一起移除)。
  - 成員之間「另一個」共同專案的連線保留,例如兩人也都在另一個 repo 工作,這是有資訊的。
  - 注意:`project` 連線目前用**名稱**分組(`crystals.ts`)。比對可以先用名稱,之後 `project` 連線改用專案代號(M5a 審查 B2 的方向)時,再改成用代號比對。
  - 右上角「◇ 同專案」開關在星系內部可以保留,用來控制「其他共同專案」的連線。

### S2 小星系的內部畫面擠在中央、四周大片空白(建議,高優先)

- 位置:星系內部直接用 M5a 的 `StarMap`(`GalaxyView.tsx:357`)。水晶座標是 M5a 的**全域**座標(半徑 220–340 的球殼);`screen-layout.ts` 的 `fitViewport` 只會縮小(`factor` 上限 1),不會放大。
- 情境:「星核」只有 6 顆水晶,但它們的座標是在全部節點一起擺放時決定的,分散在大球殼上。投影後只佔畫面中央約 450px,四周大片空白,而且因為深度不同,水晶和銘牌互相重疊(截圖中「星核 · 2」「星核 · 1」擠在一起)。
- 修法建議(擇一,或兩者都做):
  1. **允許放大**:星系內部的 `fitViewport` 允許 `factor` 大於 1,依成員外框放大,上限約 1.6,讓小星系填滿舞台的六到七成。這是改動最小的做法。
  2. **內部用自己的座標**:星系內部對成員另外做一次 `placeNew`(只用這個星系的成員,固定存在 `crystal-layout.json` 的星系子鍵)。這樣小星系分布更均勻。代價是同一顆水晶在平面星圖和星系內部的位置不同,但星系模式下本來就不會同時看到兩者。

  建議先做 1,畫面擁擠的問題再用 2 解決。

### S3 整理的平滑移動用的計時器沒有在卸載時清掉(建議,低)

- 位置:`GalaxyView.tsx:240`(`window.setTimeout(() => setArranging(false), 650)`)。
- 情境:整理動畫進行中,如果使用者切換記憶庫(`Sky` 依記憶庫 `key` 重新掛載)或離開樓上,計時器仍會對已卸載的元件設定狀態。React 19 不會報錯,不會造成實際問題,但和其他元件「所有計時器都有清理」的做法不一致。
- 修法建議:用 ref 保存計時器,在 effect 的清理函式裡清掉。

### S4 「同時參與的專案」用名稱比對(建議,低)

- 位置:`Sky.tsx`(`alsoIn = node.projectNames.filter(name => name !== homeName)`)。
- 情境:`projectNames` 是統計檔的專案名稱加上判例的專案名稱,用**名稱**去重。兩個同名、不同路徑的專案(例如都叫 `app`)會被合併,而且其中一個如果是主星系,另一個會被一起濾掉。清單裡也會出現共用資料夾這類非星系的專案。
- 修法建議:
  - 改由主程序回傳 `星系代號 → 名稱` 的清單(例如 `readCrystal` 附上這個節點的專案代號清單),畫面用代號去掉主星系。
  - 名稱只用來顯示,並標出哪些是小星雲。

### S5 DOM 屬性裡有 `p_` 代號(建議,只需確認)

- 位置:`data-group`、`data-bridge`、`data-promote`、`data-galaxy-interior` 的值是 `p_` 代號。
- 判斷:`p_` 是不透明代號,不是路徑,§11 允許送到畫面(`MemoryEntry.projectId` 早已這樣做),畫面文字裡也沒有代號或路徑,測試「畫面沒有路徑或專案ID」有涵蓋。所以**可以接受**。只要注意 M5e-a 審查 B4:代號沒有加鹽,有人猜到路徑就能確認,但 DOM 只在本機。

### S6 vault keeper 的三個疑慮(建議,可以接受)

| 疑慮 | 評估 |
|---|---|
| 星橋穿過其他星系 | 可以接受。星橋畫在星系下層(SVG 在群組之前),彎度 14%,不會遮住星系本體或銘牌。如果之後星系變多,可以加一個簡單的避讓:控制點的彎曲方向改成「避開中點附近的第三個星系」,但第一版不必做。 |
| 「整理一次」沒有驗證實際位移 | 應該補測試,見第四節 T2。目前的測試只驗證文案、按鈕和「確認後才呼叫 `arrangeGalaxies`」,沒有斷言「新座標確實套用,而且有 650ms 的位移過程」。 |
| 星系在畫面上的位置不是永遠固定 | 可以接受,但要在 §6.10 註明。**抽象座標固定**(存在 userData);畫面位置會隨視窗大小和群組數量調整,包括縮放和避免重疊時的推開。推開只沿兩群的連線方向,不會讓星系換到另一側,相對方位維持不變,符合「位置固定」想保護的空間記憶。 |

### S7 讀取星系資料失敗時,一律退回平面星圖,沒有提示(建議,低)

- 位置:`Sky.tsx`(`listGalaxies` 失敗時設成 `{ enabled: false }`)。
- 情境:如果是暫時性的讀取失敗(例如 userData 的 `galaxy-layout.json` 被鎖住),使用者會突然看到平面星圖,不知道為什麼星系不見了。下一次重新整理才會恢復。
- 修法建議:讀取失敗時保留上一份星系資料;第一次讀取就失敗時,才退回平面星圖,並在舞台角落顯示一行「無法讀取專案星系,暫時顯示平面星圖」。

## 三、狀態機、焦點、和既有功能的互動

| 項目 | 結果 |
|---|---|
| 飛入與返回 | 550ms ease-out;總覽放大 1.6 倍並淡出,內部從 0.94 倍淡入;低動態時 150ms 交叉淡換 |
| 連點 | 飛行中再按,直接落到所按方向的終態(和樓層切換相同的規則),不留排程,有測試 |
| 動畫中點選優先 | 使用者在飛行中選了其他星系,會清掉 `pendingSelect`,跳轉請求不會覆蓋使用者的操作 |
| Esc 分兩段 | 星系內部有選取時,第一次 Esc 關履歷欄,第二次飛回總覽;頒發視窗的 Esc 會攔下,不會連帶觸發 |
| 跳轉先飛入再選取 | 先飛進節點的主星系,`onArrived` 之後才選取並移動焦點 |
| 平面星圖退路 | `enabled: false`、沒有 API、讀取失敗都顯示平面星圖;還不知道結果時顯示空舞台,不會閃現平面星圖 |
| 焦點 | 飛入後到「返回星系總覽」,飛回後回到剛才那個星系的按鈕 |
| 清理 | 飛行控制器卸載時 `cancel`;提示條計時器有清理;S3 的整理計時器例外 |
| 和 M5b 樓層切換 | 在樓下時就先讀星系資料,樓層切換抵達時畫面已經決定;樓上的目標星系跨樓層保留 |
| 和 M5a 星圖相機 | 星系內部直接用 `StarMap`,相機、銘牌避讓、密集縮放照舊;每次飛入用 `key={shown}` 重建,不會帶上一個星系的視角 |
| 和 M5c 光暈與頒發 | 星系內部的水晶沿用光暈等級;頒發視窗和兩段 Esc 不衝突 |
