## 必修

### R1 本機路徑(專案ID、工作目錄)經 IPC 送到介面

- 位置:`src/shared/types.ts`(`MemoryEntry.projectId`)、`src/main/vault/index.ts`(`entryDetail` 的 `attributes`)、`src/renderer/library/Library.tsx:271-280`、`ReadingDesk.tsx:100`
- 情境:記憶檔的 `專案ID` 是主控台寫入的**本機路徑**(例:`d:/…/某專案`)。目前
  1. `listEntries` / `search` 回傳的每筆 `MemoryEntry.projectId` 就是這個路徑;
  2. `readEntry` 的 `attributes` 原樣包含 `專案ID`;M5 的節點側寫/封存檔還會帶 `工作目錄`(同樣是本機路徑)。

  介面雖然用 `isProjectIdAttribute` 把它從屬性表藏起來、書閣選單顯示名稱,但路徑已經在介面的記憶體裡,任何未來的顯示錯誤、例外訊息、開發者工具、記錄都可能洩漏。這違反「專案ID 不得出現在 IPC 回傳給介面的資料中」。
- 要求:
  1. 主程序把 `projectId` 換成不透明代號再送出(例:`'p_' + sha256(projectId).slice(0, 12)`);篩選仍用這個代號比對,介面不需要知道原值。
  2. `attributes` 送出前移除 `專案ID`(含別名 `專案id`、`project-id`、`projectId`)與 `工作目錄`;判斷規則放在主程序(`src/main/vault/`),介面的 `isProjectIdAttribute` 可留作第二道防線。
  3. 補測試:`listEntries`、`search`、`readEntry`、`readCrystal` 的回傳(序列化後的 JSON 字串)不得包含 fixtures 裡的 `d:/synthetic/` 字樣。

### R2 回收區已有同名檔時,該卷宗永遠無法再移入回收

- 位置:`src/main/vault/write.ts:128`(`recycledPath = '_回收/' + key`)、`:158`(`occupied`);`src/renderer/library/use-vault-writes.ts:25`
- 情境:使用者把 `preferences/報表時間格式.md` 移入回收 → 之後主控台又寫出同名的新偏好(主控台以標題產生檔名,同名很常見)→ 使用者再移入回收時,`_回收/preferences/報表時間格式.md` 已存在,回傳 `occupied`。介面顯示「未儲存 · 目的地已有同名卷宗,兩份都保留」,重試永遠失敗;使用者只能自己去檔案總管清回收區。訊息也有誤導:回收並沒有完成。
- 要求:
  1. 移入回收時,若 `_回收/<key>` 已存在,改用加序號的檔名:`_回收/<資料夾>/<原檔名> (2).md`、`(3)`…(上限例如 99,超過才回 `occupied`);用 `link` 的 `EEXIST` 判斷,保持現有的「目的地為空才發布」原子性。回傳實際的 `recycledPath`,撤銷照用。
  2. 還原(撤銷)時的 `occupied` 維持現狀(不覆蓋、回收區那份保留),但訊息改成「原位置已有同名卷宗,未還原;回收區的那份仍保留」。
  3. `reasonText` 依動作區分 `occupied` 的文案(回收 vs 還原)。
  4. 補測試:同一路徑回收兩次 → 第二次成功且得到 `(2)` 檔名;撤銷第二次的回收能正確還原。

現有測試品質不錯:位元組級比對(BOM、CRLF、註解、未知欄位、非 UTF-8 位元組)、並發第二筆寫入被擋、暫存寫完後外部追加會中止且清掉暫存、撤銷時同名檔最後一刻出現的保留兩份,都是真正會失敗的斷言,不是空轉。
