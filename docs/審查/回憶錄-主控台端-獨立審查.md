## 必修

### 1. 回憶錄請求不會過期,節點之後隨時都能提交(`src/main/memory-draft.ts:176-227`)
- **狀況**:使用者按「寫回憶錄」之後,請求記在設定裡,重開主控台也還在。只有三種情況會清掉:提交成功、`submitMemoir` 裡的上限檢查、`cancelMemoir`(只有刪除流程會呼叫)。
- **失敗情境**:節點那一回合結束時沒有呼叫 `memory_draft`,請求就一直掛著。幾天後別的節點透過 `ask_node` 或會議叫它寫,它照樣可以提交,繞過「要主控台請求才能提交」的規則。
- **連帶風險**:每個節點的互叫權杖以明文寫在 `interop.dir/<agentId>.json`(`interop.ts:355-358`)。所有節點都用同一個使用者的檔案權限執行,一個節點可以讀到別人的權杖、冒用身分呼叫 `memory_draft`。請求不過期,冒用就有機會寫進回憶錄。權杖明文存放是 9d6b1b6 之前就有的問題,`case_submit` 也受影響。
- **建議修法**:只在該節點的回憶錄回合正在執行或排隊時接受提交(`memoirActive`),或者加時限(例如沿用 `DRAFT_RETRY_MS`);回憶錄回合結束卻沒有提交時清掉請求。請求掛著但沒有在進行的情況,重新請求就能涵蓋。

### 2. 主控台接受的章節標題寫法,寶庫認不出來(`memoir.ts:77-87` `h2Name`、`memoir.ts:110-122`)
- **狀況**:主控台把 `## 來源:`、`## 來源:`(全形冒號)、`## **來源**` 都當成固定章節,也會略過 `<!-- -->` 註解裡的標題。寶庫 M7 的 `splitMemoirSections` 原本只認完全相同的「來源」「不確定之處」,也不略過註解。
- **失敗情境**:節點寫 `## **不確定之處**:`,主控台收下,寶庫卻拆不出「不確定之處」,閱讀桌少了置頂的不確定之處框,內容混進正文與摘要。被註解掉的 `## 來源` 則會在寶庫變成第二段來源。
- **寶庫端已修**(本次,vault keeper):回憶錄章節標題比對前先拿掉粗體記號與結尾冒號(`entry.ts` 的 `memoirSectionTitle`);以 `<!--` 開頭的整行註解區塊裡的標題不算(`markdownHeadings`)。測試:`src/main/vault/memoir-sample.test.ts`。
- **主控台端仍建議**:寫入時把收下的固定章節標題改寫成標準的 `## 來源`、`## 不確定之處`,讓檔案本身一致,其他讀者(例如 `memory_read` 的節點)也不會困惑。

## 建議

3. **章節檢查有誤收與誤拒**(`memoir.ts:97-138`,子代理用實際的 `checkSections` 逐一確認):
   - 誤收:HTML 區塊(`<pre>` 內)裡的標題會被接受;只有空的程式碼圍欄、一條 `---` 分隔線或只有連結參照的章節會被當成有內容。
   - 誤拒:正文的行內程式碼裡寫了 `<!--`(例如 ``用了 `<!--` 標記``),會被當成註解開頭,吞掉後面所有文字,導致「缺少 ## 不確定之處」,錯誤訊息也看不出原因。
   - 建議:行內程式碼裡的註解記號不算;圍欄與分隔線不算內容;`<pre>`、`<details>` 區塊比照圍欄處理。
4. **刪除節點流程**(`memoir.ts:263-283`、`core.ts:585-595`):
   - 節點已經提交成功,但回合超過 3 分鐘時,逾時分支仍會中斷回合並回報「節點沒有在時限內寫完回憶錄」。建議:請求已不在時,回報已寫完。
   - 逾時時 `interrupt()` 沒有等待,`archiveNode` 立刻執行;`selfOk` 需要 `state === 'idle'`,使用者選的「請節點寫工作總結」就會默默改成總管代寫或不寫。建議:歸檔前有上限地等節點回到待命。
   - 最壞情況使用者要等 9 分鐘(回憶錄 3 + 自己寫總結 3 + 總管代寫 3);畫面寫「最多各等 3 分鐘」。刪除不會被擋,符合規格。
5. **樣本檔**:`tools/make-memoir-sample.mjs` 用的是真正的 `parseMemoir`、`buildMemoir`、`serializeFrontMatter`,重跑可逐位元組重現;實際 `writeMemoir` 的輸出除了檔尾註解也相同。但檔尾兩行 `<!-- -->` 是真實檔案沒有的,寶庫的交叉驗證測試要先去掉。建議:改成用 `writeMemoir` 寫進暫存記憶庫再複製,說明文字放在樣本正文以外的地方。
6. **本機路徑遮罩的缺口**(`meeting-record.ts:78-86`,會議紀錄共用,9d6b1b6 之前就有):`/root/…`、`/opt/…`、`/var/…`、`/tmp/…`、`/Volumes/…` 沒有遮;`see /home/bob/projects/x and ~/y` 會被整段吃成 `see [本機路徑已隱藏]`。
7. **兩邊判斷「種類」的規則不同**:主控台只要 `種類: 回憶錄` 就當回憶錄,不管在哪個資料夾;寶庫只有 `memoirs/` 底下的才算。administrator 遷移那四份舊檔時要注意:搬之前主控台會把它們當回憶錄而隱藏(直到已確認),寶庫卻當知識顯示。遷移說明應寫明。

## 小問題

- `parsePeriod` 不接受 `2026-01-01/`(寶庫接受;主控台規格本來就只寫 `YYYY-MM-DD`),也不接受西元 0000–0099 年(`Date.UTC` 會換成 1900 年起)。
- 每日上限已滿時的告別請求回「…明天再寫」,對要被刪除的節點沒有意義;刪除對話框在這種情況下仍會問要不要寫回憶錄。
- `Dialog.tsx`:`rm` 是元件內狀態,刪除等待中關掉再打開對話框,「寫回憶錄」「儲存這段記憶」會重新啟用,違反第六輪 §6「刪除等待期間停用」(後端仍會擋重複請求)。「寫回憶錄再刪除」快速連點可能呼叫兩次 `removeAgentArchived`(工作總結按鈕原本就有同樣的寫法)。
- `memory-draft.ts:223`:計數用第二次呼叫的 `this.now()`,而鍵值用 `now`,跨午夜時會算錯;`memoir:count:*` 鍵從不清理;沒選回憶錄就刪除的節點,其請求會留在設定裡。
- 回憶錄回合的判斷依提示開頭(`isMemoirPrompt`);別的節點的 `ask_node` 提示若以 `MEMOIR_PROMPT_LEAD` 開頭,或使用者改了排隊中的內容,就能假造或隱藏「回憶錄回合進行中」。
- 寶庫規格 5.15 提到用 `取代:` 隱藏改寫前的舊章,但 `memory_draft` 的 kind memoir 沒有 `supersedes` 參數。主控台規格沒有要求,只是記下這個落差。

## 檢查過、沒有問題

- **身分**:`節點ID`、`節點`、`後台` 一律取自權杖的 `callerId` 與節點資料;子代理被拒;節點自己填的身分、狀態、範圍欄位一律忽略。
- **請求規則**:回憶錄請求與一般草稿請求不能互換;一次請求只能提交一份;格式不合格時請求保留,讓節點重寫;`memory_write` 拒寫回憶錄。
- **遠端**:`requestMemoir` 需要 operate 權限(同 `requestDraft`);`removeArchived` 只限完整權限,`memoir === true` 嚴格比對。
- **可見性**:`memory_search`、`memory_read`(含直接給路徑、不分大小寫)都套 `statusVisible`;未確認或退回的回憶錄不影響取代關係、伺服器端 `[[…]]` 解析、封存與統計,沒有外洩。
- **每日上限**:`submitMemoir` 在上限檢查、寫檔、計數之間沒有 `await`,同一程序內不會競態;請求時與提交時都檢查。
- **檔頭**:標題裡的換行、NEL、引號、反斜線、`---` 都壓成一行並跳脫,`parseFrontMatter` 讀回正確(子代理實測來回);`涵蓋期間` 嚴格驗證。
- **檔名與路徑**:節點名稱或 ID 裡的 `..` 跳不出資料夾;Windows 保留名稱因為有日期前綴與 ID 後綴而無害;同名加 `-2`、`-3`,包括長標題截到 60 字後撞名。
- **遮罩**:標題裡的 Windows 路徑在檔頭與檔名都被遮;標題裡的金鑰在檔頭(`serializeFrontMatter`)與檔名都被遮。
- **範圍**:沒有定時喚起,也沒有 `entropy-nexus://memoir` 協定。
