## 二、建議

### B1 頒發峰值之後才發生的退回,不會反映到「有效完成數」(建議,高優先)

- 位置:`glow-peaks.ts:84-92`(只有 `完成數` 超過舊峰值時,才更新 `退回數`)、`glow.ts:88`。
- 情境:
  1. 節點完成 100 件,0 件退回,記下峰值 `{100, 0}`。
  2. 使用者之後回頭把其中 30 件標成退回。被退回的任務狀態仍是 `done`,所以 `完成數` 還是 100,沒有超過峰值,峰值不更新。
  3. 有效完成數仍是 100 − 0 = 100,完成項維持 +10 分。

  退回率閘門用的是目前窗口(30%),所以等級會被擋在藍,這是正確的。但如果退回分散在多個時期、窗口內退回率始終低於 20%,舊的退回就永遠不會從分數裡扣掉。這是一條「誤升」路徑。
- 修法建議:峰值另外記錄「看過的最大退回數」,有效完成數改成 `完成峰值 − max(退回峰值, 目前退回數)`。測試補一個案例:峰值之後退回增加,有效完成數要下降。

### B2 退回率的分子包含失敗任務上的退回(建議)

- 位置:`glow.ts:97`、`glow.ts:88`。
- 情境:這是主控台的事實。使用者可以對失敗或中斷的任務按「退回」,這些退回會算進 `退回數`,但這些任務不在 `完成數` 裡。結果有兩個:
  - 退回率被高估。失敗任務很多、使用者又習慣都按退回的節點,會被 20% 的閘門誤擋。
  - 有效完成數多扣。
- 修法建議(擇一):
  - 寶庫端在徽記說明加一句「退回包含失敗任務上的退回」。
  - 請主控台另外提供「完成且退回」的數字,我可以加,要改主控台,屬於小改。

  在主控台補上之前,第一種做法就夠了。

### B3 參與判例會把總管和會議旁聽者都算進去(建議)

- 位置:`crystals.ts`(`participatedCases = confirmed.length − handled.length`)。
- 情境:這是主控台的事實。`參與節點ID` 包含交辦者,會議交辦的還包含整場會議的參與者。所以:
  - 總管每交辦一件、而且之後確認成判例的任務,都算一次參與。
  - 沒發言的與會者也算。

  有 +10 的上限,影響有限。但總管這類節點會因此穩定拿到 10 分,較容易到綠晶,這和「參與 = 協作貢獻」的原意有落差。
- 修法建議:
  - 排除統計檔 `總管: true` 的節點(主控台已在 commit `d82ac10` 提供這個旗標)。
  - 或在 §6.9 註明「參與包含交辦者與會議參與者」。

### B4 跨專案數把非 git 的共用資料夾也算成專案(建議)

- 位置:`crystals.ts`(`statsProjects` 取全部 `專案` 代號)。
- 情境:
  - 節點如果待過共用的 test 資料夾,這個資料夾就算一個「專案」,+4 分。
  - 有人在多個雜務資料夾之間切換,可以累積到 6 個「專案」、+24 分,這正是 §6.9 想防的灌水。

  主控台今天已經在統計檔提供 `專案表`,裡面有 `類型: git | 資料夾`(commit `d82ac10`),和 §6.10 的「只有 git 才算星系」同一個依據。
- 修法建議:跨專案數只算 `專案表` 裡 `類型 === 'git'` 的專案。沒有 `專案表` 的舊統計檔照現行做法,等於近似值。

### B5 頒發後立刻再操作,可能撞上自己造成的版本衝突(建議)

- 位置:`Sky.tsx:99-111`(`setAward` 用的是 `data.awards.version`;寫入成功後才觸發 `reload`,重新讀 `listCrystals`)。
- 情境:頒發成功後,在 `listCrystals` 回來之前立刻按「撤回」,會帶著舊版本送出,得到「剛被其他程式修改」。結果是安全的,但訊息會誤導使用者。

  vault keeper 回報的「外部改檔後第一次操作會撞衝突」是同一個機制。那種情況是預期中的,也是正確的:外部修改後本來就應該先重新載入。
- 修法建議:
  - 寫入成功時,立刻用回傳的 `{ mtime, size }` 更新本地的 `data.awards.version`。
  - 也可以讓 `readCrystal` 一併回傳頒發檔版本,讓兩條讀取路徑一致。

### B6 頒發理由沒有遮罩(建議,視規格而定)

- 位置:`glow.ts:158-162`(`normaliseAwardReason` 只處理換行和長度)、`awards.ts:121`。
- 情境:理由原樣寫進記憶庫根目錄的 `.vault-awards.json`。如果使用者在理由裡貼了金鑰或本機路徑:
  - **顯示時**:IPC 出口的 `redactForRenderer` 會遮掉路徑,但金鑰不會被遮。
  - **檔案裡**:兩者都會留著原值。

  主控台寫入記憶時會遮罩金鑰(`maskSecrets`)。管理指示裡提到「理由的長度與遮罩」,如果規格要求遮罩,目前沒有做到。
- 修法建議:寫入前套用和主控台相同規則的金鑰遮罩;路徑則照 §11,以出口遮罩為準即可。

## 三、頒發檔:主控台真的不會碰

- **不會讀**:主控台的 `memory-vault.ts` 只掃 `nodes`、`cases`、`knowledge`、`preferences` 四個子資料夾底下的 `.md`。根目錄的 `.vault-awards.json` 和暫存檔 `.vault-awards-<uuid>.tmp` 都不會被索引。
- **不會寫、不會刪**:主控台寫進記憶庫根目錄的只有三種檔案:
  - `.nexus-heat.json` 和 `.nexus-stats.json`。
  - 它們各自的暫存檔,命名是 `<檔名>.<pid>.tmp`。
  - `說明.md`。

  主控台沒有任何刪除根目錄檔案的程式。
- **不會被誤動**:主控台的資料夾監看只會觸發重新掃描 `.md`,不會動其他檔案。
- **說明檔**:記憶庫的 `說明.md` 範本已經寫明這是 App 專屬檔、主控台不讀不寫、請勿手動刪除(commit `e998d3c`)。舊版說明檔如果沒被改過,啟動時會換成新版。

寶庫端的寫入,經核對沒有問題:
- **原子寫入**:同一個資料夾的暫存檔加改名;改名遇到 EPERM、EBUSY、EACCES 會重試 4 次。
- **版本比對**:讀取時和改名前各比對一次版本。
- **損毀處理**:回傳 `corrupt`,不覆寫原檔。
- **保留內容**:不認得的根層鍵和個別格式錯誤的項目都原樣保留。
- **舊式 ID**:舊式路徑形態的節點 ID 會先雜湊再當鍵。

## 五、介面

- **AwardDialog**:
  - `role="dialog"` 加 `aria-modal`;開啟時焦點在理由欄(撤回時在「取消」)。
  - Tab 和 Shift+Tab 在視窗內循環。
  - Esc 會 `stopPropagation`,所以不會連帶觸發星圖的 Esc,不會收起履歷欄;寫入中時 Esc 無效。
  - 點遮罩可以取消。
  - 關閉後焦點回到原本的按鈕;按鈕因重繪被換掉時,改找新的 `[data-award-action]`。
  - 符合 §6.9 的規定。
- **GlowBadge**:可聚焦,說明用 `aria-describedby` 連到 `role="tooltip"`,懸停或聚焦都能看到。
- **低動態**:`data-quiet` 和 `prefers-reduced-motion` 都會停掉彩虹的轉動,其他等級本來就是靜態的。
  - 小提醒(建議,視覺):`rainbowSpin` 旋轉的是橢圓形的 `.crystalAura` 元素本身,所以轉動的不只是顏色,而是整個 124×152 的橢圓外形,在某些角度會看到光暈的長軸轉向。如果想要「顏色轉、形狀不動」,可以改成旋轉內層的正圓形漸層,再用橢圓遮罩裁切。
- **和 M5a、M5b 的交互**:
  - 等級只改光暈和底座環的顏色,不改尺寸,所以自動座標、密集縮放、銘牌避讓都不受影響。
  - 頒發視窗開著時,星圖的 Esc 被攔下;M5b 的跳轉不會在視窗開著時發生,因為視窗是 modal。
