## 二、建議

### B1 閱讀全文看不到 `## 回顧`,和規範不同(建議,高優先;建議改程式)

- 位置:`index.ts` 的 `readNodeProfile`(`profileSections(...).body` 是去掉回顧後的正文)、`profile-content.ts:36-40`。
- 情境:
  - §6.6.1 規定回顧「依閱讀紙規則放在最後的『回顧』小節」,實作卻完全不回傳。
  - 編輯時的正文**包含**使用者的回顧(`parts.user` 只在補充段落處切開)。結果是使用者在「閱讀全文」看不到回顧,按「編輯」卻看得到,兩邊不一致。
- 判斷:讓 agent 讀不到回顧,是為了讓 agent 的上下文乾淨(主控台的 `memory_read` 預設不含回顧)。寶庫是使用者自己的管理介面,沒有理由對使用者隱藏。
- 修法建議:**改程式,不改規範**。`ReadableNodeProfile` 加上 `review`,放在閱讀紙最後的「回顧」小節。補充段落各自的回顧也一併保留。

### B2 補充段落唯讀,但規範寫成可以編輯(建議,高優先;建議改規範,並補一個動作)

- 位置:`profile-content.ts:56-82`、`:114-128`(補充段落整段原樣保留,編輯時如果出現補充標記就拒絕);規範是 §6.6.2「範圍:……含特長、流程、回顧與主控台補充段落」「使用者若要採納,自行編輯合併後刪掉該段」。
- 情境:
  - 以現在的實作,使用者**刪不掉**補充段落,只能一直累積。
  - 依第一節的事實,主控台每次附加都是整份正文,所以側寫會迅速膨脹成好幾份重複的全文。
- 判斷:補充段落唯讀是正確的安全取捨:
  - 可以避免使用者誤刪主控台剛附加、自己還沒看過的內容。
  - 也讓切分點永遠明確。

  所以應該**改規範**,寫明補充段落唯讀。但規範承諾的「採納後刪掉」流程要有替代方案。
- 修法建議:
  - **規範**:§6.6.2 改成「正文中補充段落以前的部分可以編輯;補充段落唯讀」。
  - **程式(下一版)**:每個補充段落加一個「刪除這段」動作,只刪那一段的原始位元組,同樣帶版本比對。使用者先自行把要採納的內容合併進正文,再刪掉那段。
  - **主控台端**:主控台改成只附加「有變動的章節」(例如只附加 `## 特長`),不附加整份正文,可以大幅減少重複。這要改主控台,我可以處理。

### B3 補充段落標題的時間是 UTC,畫面沒有標示(建議)

- 位置:`profile-content.ts:19-20`(`at` 原樣回傳);主控台端是 `memory-write.ts` 的 `toISOString().slice(0,16)`。
- 情境:台灣時間 11/22 下午 3 點附加的段落,標題寫「2026-11-22 07:00」。閱讀全文會顯示「主控台補充 · 2026-11-22 07:00」,使用者會以為是早上 7 點。封存檔的 `封存時間` 是本機時間,兩者並列時更容易混淆。測試名稱寫了「依 UTC 時間標題分節」,但型別、介面和 `docs/架構.md` 都沒有標示。
- 修法建議:
  - 寶庫在主程序把 `at` 當 UTC 解析,轉成本機時間再送到畫面,或另外附 ISO 字串給介面自己格式化。
  - `docs/架構.md` 註明「補充標題的時間是 UTC」。
  - 主控台不改格式,因為已經寫入的舊段落都是 UTC,改了反而新舊混雜。

### B4 喚醒的節點 ID 規則比主控台寬(建議)

- 位置:`src/main/wake.ts:20`(`^[a-z0-9][a-z0-9_-]{0,127}$`,不分大小寫)。主控台是 `^[A-Za-z0-9_-]{1,64}$`。
- 情境:
  - 長度 65–128 的 ID 會通過寶庫的檢查,送到主控台卻被拒絕,彈出「節點 ID 不正確」。
  - 開頭是 `_` 或 `-` 的 ID,主控台接受,寶庫反而拒絕。

  主控台實際產生的是 UUID(36 個字元),目前不會遇到,但兩邊的規則應該一致。
- 修法建議:改成和主控台相同的 `^[A-Za-z0-9_-]{1,64}$`,並在註解引用主控台的規則。

### B5 刪掉含路徑的那一行就無法儲存(建議)

- 位置:`profile-content.ts:110`(`seen.size !== paths.size` → `missing`)。
- 情境:正文裡的本機路徑在編輯時換成佔位符 `⟦路徑N⟧`。使用者如果刪掉一段含佔位符的文字,即使是刻意刪除,儲存也會被拒絕。結果是含路徑的句子永遠刪不掉,只能保留佔位符。
- 修法建議:
  - `missing` 改成「需要確認」,不要直接拒絕:介面列出會被刪掉的路徑數量,使用者確認後再儲存。
  - `unknown`(使用者自己打的、或改壞的佔位符)和 `duplicate` 照舊拒絕,這兩種才可能造成錯誤還原。

  其他情況都已確認安全:
  - 佔位符順序被調換:依編號還原,順序不影響。
  - 原文裡本來就有像佔位符的字串:會先保留成獨立的佔位符,所以沒有修改就儲存時,內容逐位元組相同。
  - 新貼上的路徑:原樣寫入,這是使用者自己的輸入;之後閱讀時會在 IPC 出口被遮罩。

### B6 「請求已送出」的說明必須包含「請到主控台確認」(建議;要看介面文字)

- 位置:`wake.ts:31`(`ok: true` 表示 `openExternal` 成功)。
- 情境:`openExternal` 成功只代表系統把網址交給了主控台。主控台**一定會再跳確認**;使用者可能按取消,工作目錄也可能剛好不存在(主控台會說明原因)。如果畫面只寫「已喚醒」,會誤導使用者。

  這一輪我在範圍內沒有找到喚醒結果的介面文字,`DetailPanel.tsx` 的改動屬於畫面,不在這次範圍內。
- 修法建議:成功時的文字固定為「已送出喚醒請求,請到主控台確認接回」,而且不要立刻改變水晶狀態,等下一份統計檔(§6.7)。

### B7 和主控台同時寫入的極小覆蓋視窗(建議,低)

- 情境:見第一節的競態表。
- 修法建議:不必加鎖。§6.6.2 可以註明「極少數同時寫入的情況下,主控台剛附加的段落可能被覆蓋,可以在主控台請總管重寫」。

  主控台端可以補一道保護:附加前再比對一次 mtime,有變就重讀再附加。這要改主控台,屬於小改,可以和 B2 的主控台改動一起做。

### B8 編輯封存節點時,改的是封存檔(建議,只需確認)

- 位置:`index.ts` 的 `nodeProfilePath`(封存節點的 `profile` 是最新一份封存)。
- 判斷:這符合 §6.6.2「寫回的檔案就是閱讀全文開啟的那一份」。但要讓使用者知道:主控台的「接回封存」會從**最新封存檔**抽出 `## 特長` 和 `## 解決問題的流程`。所以使用者對封存檔的編輯,會在下次接回時帶進新節點。這是好事,值得在編輯畫面提一句。

## 四、隱私與 IPC 出口

- **路徑對照表**:佔位符和路徑的對照表 `ProfileDraft.paths` 只存在主程序的記憶體(`profileDrafts`),不經過 IPC、不寫檔、不寫日誌;錯誤回傳只有原因代碼。
- **閱讀全文**:正文和補充段落都經過 `redactForRenderer` 遮罩絕對路徑。`source.path` 是記憶庫內的相對路徑(`nodes/…`),§11 允許。
- **編輯正文**:絕對路徑在送出前已經換成佔位符,再經過出口遮罩也沒有影響。
- **專案ID**:這次新增的 IPC 回傳都沒有專案ID。

## 六、規範差異:哪些改規範、哪些改程式

| 差異 | 建議 |
|---|---|
| 閱讀全文省略回顧(§6.6.1 要求顯示) | **改程式**,顯示回顧(B1) |
| 編輯時保留使用者的回顧(使用者可以編輯自己的回顧) | 符合 §6.6.2「含……回顧」,不用改 |
| 補充段落唯讀(§6.6.2 寫可以編輯) | **改規範**,寫成唯讀;下一版補「刪除這段」動作(B2) |
| 特長取使用者版本的第一個 `## 特長` | 和 §6.6.2、主控台的結構一致,不用改 |
| 補充段落的時間 | 規範和架構文件都要註明是 UTC,程式要轉換或標示(B3) |
| 喚醒成功的語意 | §6.7 已經寫「主控台會再跳一次確認」,介面文字要照著寫(B6) |

**需要主控台配合的事項(由我處理,要先經過同意)**:
- 補充段落只附加有變動的章節(B2)。
- 附加前再比對一次 mtime(B7)。
